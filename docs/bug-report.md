# タスクバーをクリックしても最前面へ戻せない

## 症状と原因

最前面表示の設定は起動時と通知領域からの復元時だけで、クリック時には再設定していなかった。
WebView2内のマウス操作はWPFのマウスイベントへ伝わらないため、WebView側からクリックを通知する必要がある。

## 修正

- WebView全体のマウスボタン押下をキャプチャし、タスク項目や余白からホストへ通知する。
- `SetWindowPos` の `HWND_TOPMOST` でタスクバーを最前面へ再設定する。
- 位置・サイズとフォーカスを維持し、通知領域への最小化中は再設定しない。
- 再設定に失敗した場合はWin32エラーをログに記録する。

## 検証

- WebViewのTypeScript型チェック・ビルド成功。既存テスト5件成功。
- .NET SDKがないため、WPF本体のビルドは未実施。
- Windows実機での最前面表示・クリック操作の確認は未実施。

# Claudeのサブエージェント待機中に完了表示になる

## 症状と原因

Claudeの親がバックグラウンドのサブエージェントを待つために応答を止めた場合も、`Stop` が発生する。
通知スクリプトは常に `completed` を送っていたため、作業が続いているのに完了アイコンになっていた。

## 修正（0.1.11）

- `Stop` の `background_tasks` に `running` / `pending` の処理がある間は `running` を送る。
- `onlyIfActive` を付け、中断・終了後に届いた待機中の通知で表示を戻さない。
- 子の終了を直接完了とは扱わず、バックグラウンド処理がなくなった親の最終 `Stop` で完了を通知する。
- 拡張名を維持して0.1.11へ更新し、フックスクリプトの再配置手順をREADMEに記載する。

## 検証

- TypeScriptの型チェック・ビルド成功。拡張テスト69件成功、ローカルTCP通信が禁止されているため通信テスト3件はスキップ。
- 複数のサブエージェントの実行・待機中、一部だけが終了した場合、親の最終応答での完了通知を確認。
- 通常の完了、質問・中断・終了通知、導入済みフックコマンドでの状態通知を確認。
- VSIX 0.1.11を作成し、バージョン・通知スクリプト・コンパイル結果の一致を確認。
- ユーザーによるCodexのサブエージェント表示確認では問題なし。Claude実機での表示確認は未実施。

## 適用条件

`background_tasks` を渡すClaude Codeが必要（2.1.291のイベント定義で確認）。フィールドがない旧版は従来の完了判定となる。
Claudeを実行するコンテナ内で `python3 VSCodeExtension/scripts/install-claude-hooks.py` を再実行し、Claudeを起動し直す。
VSIXの更新だけでは配置済みの通知スクリプトは更新されない。

# VSCode再起動時にターミナルの再起動要求が出る

## 症状と原因

VSCodeを再起動・再読み込みすると、WpfTaskBar AI Statusによるターミナル環境変数の再適用を求められる。
0.1.9ではWpfTaskBarへの再接続中だけIDが固定され、拡張の起動ごとに新しいIDを生成していた。
環境変数コレクションの永続化を無効にし、起動時と終了時にクリアしていたため、復元ターミナルのIDと一致しなかった。

## 修正（0.1.10）

- VSCodeがワークスペースごとに保存する環境変数コレクションを永続化し、保存済みの通知IDを再利用する。
- 起動時・終了時に環境変数を消さず、値が変わった変数だけを更新する。
- 終了時は本体の登録を解除し、次回は同じIDで現在の通知先に再登録する。
- READMEに更新時の移行手順と、通知先URLなどが変わる場合の再起動条件を記載する。
- 拡張名を維持して0.1.10へ更新し、同名のVSIXを作成する。

## 検証

- TypeScriptビルド成功。拡張テスト67件成功、ローカルTCP通信が禁止されているため通信テスト3件はスキップ。
- 再起動を模した環境変数コレクションの復元で、同じIDの再登録と環境変数の書き換えがないことを確認。
- 本体停止中の再起動、別ワークスペースのID分離、通知先URL変更時の差分更新を確認。
- VSIX 0.1.10を作成し、拡張名・バージョン・コンパイル結果・READMEの一致を確認。
- Windows実機でのターミナル復元・再起動要求の表示確認は未実施。

## 移行時の制限

0.1.9以前はIDを保存していないため、更新直後はターミナルとコンテナを一度開き直す必要がある。
以後は同じワークスペース・通知先URLなら開き直し不要。拡張のアンインストールや保存データ削除でIDを失った場合も再作成が必要。
VSCodeの表示設定を変更して通知を一律に隠す処理は追加しない。

# AI通知が別のVSCodeウィンドウに表示される（0.1.9の修正）

## 症状と原因

複数のVSCodeウィンドウを開いていると、AI通知が別のウィンドウに表示されることがあった。
拡張が起動時にウィンドウ一覧の先頭を自動選択し、拡張自身のウィンドウとの一致を確認していなかったため。
また、通知先を手動で変更するとセッションIDを再発行していたため、変更前のIDを持つターミナルやコンテナを起動し直す必要があった。

## 修正

- 初回は拡張自身にフォーカスがある間に前面のHWNDを取得して自動登録する。背景で起動した拡張はフォーカスを待つ。
- 取得中のフォーカス変更では候補を捨て、登録直前にも本体側で同じHWNDが前面にあるか確認する。一度外れて戻った場合も取得をやり直す。
- 前面を確認できない場合は手動選択に戻り、キャンセル時は未登録で待機する。登録済みの通知先はフォーカス移動では変更しない。
- 通知先の変更ではセッションID・状態・通知本文を維持し、HWNDとPIDの紐付けだけを変更する。
- タスクバーの右クリックメニューに「AI通知先を変更」を追加する。
- 拡張は本体側の紐付けを読み取り、生存確認でも変更後の通知先を取得して、再接続に使う。
- 無効な通知先への変更を拒否し、古いウィンドウの失効処理が変更後の紐付けを削除しないようにする。
- VSCode拡張を0.1.9へ更新する。本体も前面ウィンドウの取得・登録時の確認に対応したバージョンへ更新する必要がある。

## 検証

- VSCode拡張のTypeScriptビルド成功。前面判定・フォーカス変更・手動選択への切り替えを含め、テスト63件成功。
- ローカルTCP通信が禁止された環境のため、通信テスト3件を明示的にスキップ。
- WebViewのビルド成功。既存テスト5件成功。
- VSIXを作成し、拡張名・バージョン・コンパイル済みファイルの一致を確認。
- APIと状態管理の回帰テストを追加。.NET SDKがないため、C#テストとWPF本体のビルドは未実施。
- Windows実機での通知先変更・表示確認は未実施。

## 残る範囲

初回に自分のウィンドウへフォーカスが来るまでは自動登録しない。前面取得だけで拡張の所属を直接取得できるわけではないため、フォーカス状態との照合を行う。
0.1.9ではセッションIDは拡張の稼働中だけ固定だった。再起動・再読み込み時の維持は上記0.1.10で対応。
